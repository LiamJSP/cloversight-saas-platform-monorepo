# Provider secrets and verification key rotation

Release 0.5.13 evicts a rejected AWS runtime initialization and retries on a later invocation. Successful runtime graphs are rebuilt on first use after five minutes; Stripe and Twilio credentials are reread through a five-minute secret cache. The HTTP router follows the new graph. Existing invocations finish with their original graph. This refresh adds occasional SDK client/schema initialization work and does not cache tenant authorization or financial state.

Provider credential rotation must allow the old credential to remain valid during that overlap, then revoke it after every relevant function has refreshed and in-flight work has drained. If a compromised credential cannot remain valid, revoke immediately and use the provider's recovery procedure; requests during propagation can fail. Inspect payment reconciliation before retrying a charge. Do not automatically repeat a provider mutation whose success is ambiguous.

Response/price integrity keys and CloudFront origin verification keys remain cached for the life of a warm process. They require coordinated deployment and recycling of the affected functions. Changing a Secrets Manager value alone does not complete those rotations. The response-token implementation still accepts one key, so automatic overlapping verification-key rotation is deferred. Inventory outstanding response/unsubscribe/report links and signed price calculations before replacing the integrity key; arrange a supported transition or explicitly accept invalidation and recovery. Never promise old links remain usable after a single-key replacement.

Stripe webhook verification also currently accepts one secret. Arrange the provider endpoint rollover and a controlled function recycle/refresh; exercise both delivery/retry and event reconciliation through the owner workflow. A temporary second endpoint/key is an operational decision, not an implemented multiple-key verifier. In-flight requests can carry the old configuration until completion.

For the edge-origin secret, retain the existing `ORIGIN_VERIFY_REVISION` deployment workflow so the function configuration and CloudFront origin header move together. Complete invalidation/propagation and inspect direct-origin rejection before retiring the old secret. The current origin boundary does not accept two secrets, so a mismatch can interrupt private routes during rollout. Do not rotate it independently through the Secrets Manager console and assume the runtime will discover it.

Retain operator, time, secret version identifiers, affected functions/stages, rollout result and recovery decision in the restricted change record. Do not retain raw values in logs, audit exports, deployment notes or source snapshots. The owner must verify this procedure in staging; this source session performed no rotation or AWS calls.

AWS describes cache freshness and rotation tradeoffs in [Lambda with Secrets Manager](https://docs.aws.amazon.com/lambda/latest/dg/with-secrets-manager.html) and [Secrets Manager best practices](https://docs.aws.amazon.com/secretsmanager/latest/userguide/best-practices.html). The application's five-minute runtime policy is authored here; it is not an AWS delivery guarantee.
