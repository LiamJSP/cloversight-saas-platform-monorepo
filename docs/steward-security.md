# Steward access and accountability

## Owner bootstrap

The steward pool remains invitation-only. The platform owner is the **immutable Cognito `sub`** supplied as `STEWARD_OWNER_SUB` in the deployment environment, not a browser-controlled role or an email string. The API denies every other staff identity unless it matches an active invitation stored by the owner. Existing manually created steward users must be invited again by the owner after this upgrade. Deleting and reinviting an email binds the new Cognito subject, so an old access token cannot take over the new invitation.

For an existing stack, retrieve the intended owner's `sub` from **that stage's steward pool before deploying**. If the user does not exist, an administrator creates it with `aws cognito-idp admin-create-user` and email delivery, then retrieves the `sub`. Put it in the copied `.env` as `STEWARD_OWNER_SUB` and deploy the whole stack. Do not substitute a customer-pool subject, username, email or staff actor ID. See [deployment](deployment.md) for commands. For a brand-new stack, first deploy creates the pool with the empty parameter (staff access is denied), then create the owner, set the subject and redeploy before inviting any staff. Keep the subject stable; changing it transfers the owner role.

The owner-only **Steward Manager** invites users through Cognito's administrator API, disables/enables them, and deletes their Cognito accounts. Revocation is committed to application state before Cognito disable/delete so an already-issued access token stops working immediately. Reenablement is committed only after Cognito succeeds. A failure between Cognito creation and the application record can leave an inaccessible user in the pool; an administrator must reconcile that user rather than creating an alternate subject. Staff records and audit history survive deletion. The owner cannot be disabled or deleted from the manager.

## Activity log

Every request reaching `/api/steward/*` after gateway JWT and CloudFront origin checks receives a start record in a separate on-demand, KMS-encrypted DynamoDB table before steward authorization or operation execution. The record has the immutable actor ID, verified email, method, route path, request ID, time, hashed source IP, bounded user agent, and optional query digest; raw search strings and request bodies are excluded. Completion records response status and limited operation metadata. Staff mutation reasons and affected IDs also remain in the existing action audit collection. A failed completion write leaves a visible `started` entry; investigate these against the matching request ID and CloudWatch logs. A start-write failure blocks the action. The table has PITR and no TTL or application delete permission. The manager displays an individual owner's/steward's newest 100 requests at a time and offers older pages. Gateway-rejected invalid tokens and static page fetches never reach this application log; use gateway/edge telemetry for those.

Name search matches active account contacts and active team members by first name, last name, both, or full name, with a maximum of 25 results. A name search only returns a summary; opening an account is a separate logged request. Exact account ID/email lookup remains available. Search terms do not appear in activity records.

## Suspicious activity email

Owner-editable limits are stored in the core table and applied per steward actor with strongly consistent audit reads. Defaults: **more than 20 account searches in 5 minutes**, **more than 5 distinct accounts scheduled for closure in 60 minutes**, **more than 5 refunds in 60 minutes**, or **a single refund over 500 units of its refund currency**. The first three limits are strictly exceeded, not merely reached. Failed exact account lookups count toward searches; only successful closures and refunds count toward the other limits. The count is a rolling window, while each category/actor/window bucket has one alert claim to avoid repeated emails. Emails go to `admin@redcloversoftware.ca` through SES, independent of `STAFF_ACTION_EMAIL`, `TECHNICAL_ALERT_EMAIL` and voluntary customer email blocks. Only the owner may change the global customer block list; provider bounce/complaint restrictions remain effective for operational notices.

Each security marker records an attempt ID/count, attempt time, provider message ID and **attempted**, **accepted**, **local_queued**, **suppressed**, **failed** or **ambiguous** state. An SES message ID establishes acceptance, never confirmed delivery. A failed or ambiguous send may be retried once on the next qualifying action; an unfinished attempt older than two minutes may also be reclaimed once and records `ambiguousPreviousAttempt`. Conditional attempt checks prevent a late result from overwriting a newer claim. A stale final attempt becomes ambiguous on a later qualifying action. SES must permit the sender and recipient in its current mode. Review `steward.security_alert.failed`, `steward.security_alert.superseded_attempt` and `steward.audit_or_alert.failed` API logs. Historical markers labelled `delivered` by earlier releases are unverified legacy records, not evidence of recipient-server delivery.

This is a repair to the existing inline alert path, not a complete operational outbox. There is no autonomous security-marker retry worker or SES-feedback reconciliation in this release, and a crash after acceptance can still leave an ambiguous attempt and possible duplicate email. An independently confirmed fallback destination, dedicated operational outbox/worker, delivery feedback and heartbeat remain necessary before claiming dependable end-to-end operational delivery.

The single-refund threshold compares the nominal minor-unit amount in the refund currency; it does not perform FX conversion for legacy CAD refunds. The thresholds alert an administrator; they do not automatically block support work or reverse a refund. Adjust the settings in Steward Manager for your observed support traffic. The existing API and global transaction adapter are still the scaling limit for broad staff searches and mutations.
