# AWS deployment review — 0.5.20

Reviewed on 2026-11-17 against the available source and AWS documentation. The latest incident is `StewardSpaRewriteFunction` failing with `Rate exceeded`. That is evidence of control-plane throttling, not evidence that the account has exhausted its 100-function default quota. Account usage and current stack state were not available in this workspace.

## Findings and implemented changes

| Finding | Correction and evidence |
| --- | --- |
| Four CloudFront functions were provisioned concurrently. | Added an explicit dependency chain, retaining every logical ID, name and function body. Cache-policy and response-header-policy creation is also ordered within each API family. AWS documents that [DependsOn overrides CloudFormation parallelism](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-attribute-dependson.html). This reduces bursts; it cannot eliminate account-wide throttling. |
| An initial provisioning failure triggered a full rollback, then protected pools/nonempty buckets blocked cleanup. | New installations and resumable failed installations use `--disable-rollback`. Completed-stack updates explicitly retain normal rollback. This follows AWS's [preserve successfully provisioned resources](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/stack-failure-options.html) workflow. It does not repair an existing `ROLLBACK_FAILED` stack or turn off data protection. |
| Repeated failures required manual event commands; stale stack ARNs caused cleanup of the wrong historical attempt. | Deployment now checks the current stack before packaging/uploads, refuses blocked/in-progress states, prints the actual ARN and current-operation failures, and saves diagnostics. It never deletes a failed stack. A zero CLI exit from an empty change set is accepted only after checking stack completion. |
| Transient provisioning throttles had no bounded recovery path. | Preserved failed stacks retry at most twice after the first attempt, with increasing delay/jitter, only when every reported resource failure in that attempt is a throttle. Configuration errors, permissions, quota exhaustion and rollback failures stop. Existing-stack update failures are not automatically retried. |
| Existing preflight only recognized distribution ownership through completed stack outputs. | Ownership now comes from `ListStackResources`, including successful resources in a preserved partial create. This avoids rejecting the stack's own aliases, functions and policies on a retry. Permission errors are not treated as absence. |
| Several external prerequisites were only tested during creation. | Added read-only checks for public Route 53 zone membership, conflicting DNS records, SES receipt-rule-set existence, unmanaged SES identities, Cognito domain ownership, CloudFront name conflicts and account capacity for functions, policies, origin access controls and distributions. Existing ACM, single-image ECR manifest and Lambda reservation checks remain. Bootstrap grants the required read permissions. |
| Local validation was narrower than the available AWS schema checks; CI ignored all warnings. | `npm run iac:schema`, deployment and release verification now run pinned `cfn-lint` against all three templates and the five configured Regions. Unexpected warnings fail. Four narrowly scoped compatibility warnings are allowed: the retained legacy `BaseDomain` parameter and the optional custom Cognito certificate when its resource is disabled. AWS describes [schema validation and its limits](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/cfn-lint.html). |
| Four runtime roles contained nonexistent DynamoDB transaction IAM action names. | Removed `dynamodb:TransactGetItems` and `dynamodb:TransactWriteItems`; retained the underlying item actions and `ConditionCheckItem`. Those are the permissions [AWS actually uses for transactions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis-iam.html). No broader table access was added. |
| Regional image deployment suppressed all ECR lookup errors and persisted Docker credentials. | Missing-repository/image handling now recognizes only the specific not-found exception. Access denial and other failures stop. Registry credentials use a temporary Docker configuration removed on exit. Regional work requires a completed primary stack. |
| Regional copies relied on Docker preserving the original manifest representation. | Copy image layers, then publish the exact source ECR manifest and verify its digest. Immutable-tag retries require a matching digest readback. This accounts for [manifest-format negotiation](https://docs.aws.amazon.com/AmazonECR/latest/userguide/image-manifest-formats.html) without accepting a different image. |
| Marketing canonical links and support addresses still used the predecessor domain. | Public HTML now uses `cloversight.app`. Receiving mailboxes/aliases must actually be provisioned and tested before launch; verifying an SES sending identity does not create a support mailbox. Existing deployment defaults were retained for compatibility; keep `BASE_DOMAIN=cloversight.app` in the production environment. |

## Earlier fixes retained

All Cognito branding branches retain the supported SVG subset and valid logo/favicons dimensions. Primary and regional SQS policies retain a single-resource HTTPS denial attached to the explicit queue list. Production Cognito deletion protection and stateful-resource retention remain enabled. Existing logical IDs, deployed data, plan prices and subscription entitlements are preserved.

The review also checked the existing Lambda/SQS timeout, batching and concurrency relationships, Lambda packaging, CloudFront cache/header configurations, Cognito custom-domain parent-DNS dependency, staged DynamoDB GSI creation, and primary/regional IAM resource references. The existing safeguards in those areas remain; passing checks is not proof of live service readiness. The [Lambda SQS guidance](https://docs.aws.amazon.com/lambda/latest/dg/services-sqs-configure.html) and [Cognito custom-domain prerequisites](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-add-custom-domain.html) informed these checks.

## Verification boundary

The release gate runs deterministic service tests, JavaScript parsing, duplicate-key and application-specific IaC checks, AWS resource-schema validation, static builds and extension packaging. New tests exercise partial-stack ownership, DNS/SES/Cognito/capacity conflicts, permission failures, retry ceilings, preserved versus normal rollback, false-success prevention, and image digest preservation. Existing SVG and SQS regression tests remain included. AWS schemas are checked in `us-east-1`, `us-east-2`, `us-west-2`, `ca-central-1` and `eu-west-1`.

This review did not assume your AWS role, create/delete cloud resources, build Docker images or run live browser/Stripe/SES acceptance. Local fixtures cannot reproduce every CloudFormation provider handler, propagation delay or account-specific constraint. Preflight checks also cannot prevent another deployment consuming capacity immediately afterward. Do not run simultaneous deployments for this application.

## Remaining account-side prerequisites

- Inspect and, if necessary, recover the current failed **initial** stack using [the upgrade guide](upgrade-0.5.20.md). A template change cannot make a rollback-failed stack updateable.
- Refresh the existing bootstrap policy; rebuild the worker once from 0.5.20. Older source-contract evidence is deliberately rejected.
- Confirm operational SNS subscriptions in every Region, SES identity/DKIM and production sending access, owner enrollment/MFA, Stripe permissions/webhook delivery, regional captures and cancellation behavior before customer admission.
- SSO-to-deployment-role chaining is limited to [one hour](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html), regardless of the role's configured maximum. Keep `AWS_ROLE_SESSION_SECONDS=3600`; reauthenticate/re-run a command if credentials expire. CloudFormation may continue after the workstation session ends, so inspect status before retrying.
- Production defaults to live Stripe. The subsequent deployment-tools hotfix adds explicit `STRIPE_MODE=test`; see [the production-domain sandbox/cutover procedure](stripe-production-test-0.5.20.md).
- Preserve staging and shared bootstrap/ECR/artifact resources until production acceptance. Retire staging through a separately reviewed inventory, not by deleting shared resources during this recovery.

No pricing or entitlement changes are recommended by this deployment review. The throttle is provisioning traffic, not customer watcher throughput.
